## Обзор

Сетевые мессенджеры подвержены обрывам Wi-Fi/LTE, временной недоступности серверов, флуд-контролю (спам-банам) и дублированию пакетов при нестабильном соединении. В `neomaxz` встроена многоуровневая инфраструктура, защищающая клиент от подобных инцидентов.

## Очередь запросов и Rate Limiter (`RequestQueue`)

Доступна через `sock.queue`. Управляет исходящим потоком команд, гарантируя соблюдение лимитов сервера MAX.

### Алгоритм Token Bucket

1. **Глобальный лимит (`maxGlobalPerSecond: 30`)**: ограничивает суммарное число любых запросов к серверу от одного клиента.
2. **Изоляция по чатам (`maxChatPerSecond: 5`)**: предотвращает бан аккаунта из-за спама в один конкретный диалог. Запросы в разные чаты не блокируют друг друга.
3. **Лимит параллелизма (`maxConcurrent: 10`)**: удерживает количество одновременно выполняющихся запросов.

### Приоритеты отправки (`Priority`)

```typescript
export enum Priority {
  HIGH = 0,   // Сервисные PING, подтверждения, экстренные команды
  NORMAL = 1, // Пользовательские сообщения (по умолчанию)
  LOW = 2,    // Фоновая подгрузка истории, синхронизация
}
```

Высокоприоритетные задачи (`HIGH`) всегда извлекаются из очереди первыми, гарантируя своевременную отправку heartbeat PING даже во время массовой рассылки.

### Защита от переполнения сокета (Backpressure drain)

Если исходящий TCP-буфер сокета превышает порог `64 KB` (`bufferedAmount > maxBufferedBytes`), очередь временно приостанавливает отправку новых кадров и дожидается системного события сокета `'drain'`, исключая утечки памяти и зависания процесса.

### Методы `sock.queue`

#### `enqueue(task, options)`
Ставит задачу в очередь с контролем приоритета, ключа чата и отменой через `AbortSignal`:
```typescript
const result = await sock.queue.enqueue(
  async () => {
    return doHeavyNetworkCall();
  },
  {
    priority: Priority.HIGH,
    bucketKey: 'chat:123456',
    signal: abortController.signal,
  }
);
```

#### `clear(error?)`
Очищает очередь с отклонением всех ожидающих промисов.

#### `pendingCount`
Текущее количество задач, ожидающих в очереди.

## Предохранитель сбоев (`CircuitBreaker`)

Доступен через `sock.circuitBreaker`. Отслеживает состояние соединения на уровне L7 по задержкам ответа (RTT) на запросы `PING` (каждые 25 секунд).

### Состояния цепи

- `CLOSED` (Норма): цепь замкнута, запросы идут без ограничений.
- `OPEN` (Авария): при всплеске сбоев (по умолчанию 2 подряд) или критическом лаге сети цепь размыкается, и сокет немедленно переподключается.
- `HALF_OPEN` (Пробный период): по истечении тайм-аута (`3000ms`) выполняется тестовый запрос для проверки восстановления канала.

### Скользящий замер RTT (EWMA)

Использует экспоненциально взвешенное скользящее среднее (коэффициент $\alpha = 0.25$):

$$\text{EWMA}_{t} = 0.25 \times \text{RTT}_{t} + 0.75 \times \text{EWMA}_{t-1}$$

Если единичный RTT превышает `5000ms` или в 4 раза превышает текущую медиану `EWMA`, сокет признается «полуоткрытым» (half-dead) и немедленно сбрасывается для переподключения.

### Методы `sock.circuitBreaker`

```typescript
// Получение метрик
const { state, ewmaRtt, failures } = sock.circuitBreaker.getMetrics();
console.log(`Состояние: ${state}, Средний пинг: ${ewmaRtt}мс, Сбоев: ${failures}`);

// Принудительный сброс
sock.circuitBreaker.reset();
```

## Реестр идемпотентности (`IdempotencyLedger`)

Доступен через `sock.ledger`. Защищает от отправки сообщений-дубликатов при потере ACK от сервера из-за внезапного дропа сетевых пакетов.

### Формирование уникальных `cid`

Для каждого исходящего сообщения создается монотонный клиентский идентификатор:

$$\text{cid} = \text{Date.now()} \times 1000 + (\text{counter} \pmod{1000})$$

Вспомогательный метод `ledger.generateCid()` возвращает расширенную энтропийную строку `${timestamp}_${counter}_${randomHex}`.

### Методы `sock.ledger`

- `registerOutbound(cid, chatId)`: регистрирует исходящее сообщение в статусе `PENDING`.
- `markAcknowledged(cid, messageId?)`: переводит статус в `ACKNOWLEDGED`.
- `markFailed(cid, error)`: фиксирует сбой отправки.
- `isAcknowledged(cid)`: проверяет, подтвердил ли сервер получение сообщения с данным `cid`.
- `getPending()`: возвращает список сообщений, зависших в полете без подтверждения.
- `prune(ttlMs)`: очищает устаревшие записи (по умолчанию старше 1 часа).

## Восстановление пропущенных сообщений (`GapRecoveryManager`)

Доступен через `sock.gapRecovery`. Отвечает за бесшовную синхронизацию после переподключения.

### Монотонный учет времени и дедупликация

1. Из каждого входящего фрейма и пуш-события извлекаются `time` и `seq`, обновляя метку `lastServerTime`.
2. Кольцевой кэш на 2000 последних `messageId` фильтрует входящие дубликаты при доставке сообщений.
3. При реконнекте вызывается `performSync`, который запрашивает дельту истории с момента последнего разрыва, отсекает дубли и передает приложению только пропущенные сообщения.

### Методы `sock.gapRecovery`

```typescript
// Получение последнего известного серверного таймстемпа
const lastSeenTime = sock.gapRecovery.getLastServerTime();

// Проверка на дубликат
if (sock.gapRecovery.isDuplicate(msgId)) {
  console.log('Сообщение уже обработано ранее, пропускаем');
}
```
